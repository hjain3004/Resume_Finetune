# M8P-2 — JD-Only Positioning and Structural Selection Design

**Date:** 2026-08-23

**Status:** Approved for implementation by the user's 2026-08-23 instruction

**Phase:** 3 (M8 Tailoring)

**Predecessor:** M8P-1 (`f6cb99e`)

**Next milestone after completion:** M8P-3 (S3 alignment plus the missing deterministic G1 gates)

## 1. Goal

M8P-2 adds the two stages immediately downstream of the validated M8P-1 S1
artifact:

1. **S0 positioning:** a visible, evidence-linked strategy for how to present the
   candidate for this role.
2. **S2 structural selection:** a fabrication-proof choice of base variant,
   projects, and bullets, plus a complete coverage table for every S1
   `must_have` requirement.

This milestone still does **not** write or render resume prose. It ends at a
validated `s2.json` whose identifiers all resolve to the master profile.

## 2. Fixed boundaries

- One job at a time. There is no batch mode.
- The canonical input remains an M8P-1 `s1_request.json` plus validated `s1.json`.
- `data/jobs.db` is opened read-only only during deterministic preparation. No
  status, score, note, flag, or application row is changed.
- Only jobs that still satisfy `src.db.prepare_tailoring_request()` may proceed.
- Jobs 229 and 279 remain prohibited.
- Both model calls use the M8P-1 pure text-in/text-out boundary: no tools, no
  filesystem access, no session persistence, no shell, one attempt, no retries.
- Tests never call a real model or the network.
- Every raw model output that exists is archived through `src.llm_trace.write_trace()`.
- A failed invocation, parse, semantic check, or deterministic selection check
  never overwrites a previously accepted artifact.
- No new dependency is permitted.

## 3. Company-context decision

M8P-2 operates in explicit **`jd_only`** mode. It may use only the
`company_context` already extracted and quote-anchored by S1. It does not read
the Company Knowledge Bank, the ignored research inbox, or the internet.

This is not a degradation error. The Company Bank design explicitly permits
missing or expired company data to fall back to JD-only tailoring. Track C is
therefore not a prerequisite for the three-resume human pilot. The S0 artifact
records `context_mode: "jd_only"` so G3 can show this limitation rather than
hiding it.

## 4. Privacy-minimised master-profile projections

The existing `MasterProfile.for_tailoring(base_variant)` cannot serve S0 or S2:
it requires the base variant before S2 chooses it, exposes identity/contact data
and full phrasing text, and omits project ownership and tag structure.

M8P-2 adds two new pure projections.

### 4.1 Positioning view for S0

`MasterProfile.for_positioning()` returns frozen dataclasses containing:

- projects: `id`, `display_title`, and exact/topical keyword tags;
- experiences: `id`, `employer`, `title`, `scope_line`, and exact/topical
  keyword tags.

It omits identity, contact data, education, skills, bullet phrasing, evidence,
defense, interview risk, metric ledgers, known gaps, ownership boundaries, and
`do_not_claim`. This is enough to recommend a project or experience angle
without giving the model material it could rewrite or leak.

### 4.2 Structural selection catalog for S2

`MasterProfile.for_selection(recommended_base_variant)` returns:

- the DB/scorer-recommended base variant;
- every known base variant and its project/bullet ordering;
- every project and experience as an entry with stable id, kind, label, and
  exact/topical tags;
- every unblocked bullet with id, owner id/kind, priority, claim type, and
  `keywords_hit`;
- `do_not_claim`.

It omits all identity/contact data, education, phrasing text, evidence, defense,
interview risk, metrics, known gaps, ownership-boundary prose, and the rendered
skills taxonomy. S2 does not choose skill text; M8P-3 will derive skills only
from accepted bullet coverage. Blocked bullets are omitted rather than offered
as candidates, while the validator also rejects any unknown id fail-closed.

The current profile's numeric `priority` is the implemented strength signal.
M8P-2 does not add a second `strength` field or reinterpret the profile schema.

## 5. S0 contract

### 5.1 Request

`S0Request` contains:

- `job_id`, `company`, and `title`;
- the validated `S1Response`;
- the `PositioningView`;
- constant `context_mode = "jd_only"`.

The raw JD is not repeated. S0 receives the bounded S1 representation and its
already validated exact quotes.

### 5.2 Response

`S0Response` contains `context_mode = "jd_only"` and two to four ordered
`PositioningPoint` objects. Each point has:

- `sentence`: one nonempty advisory strategy sentence;
- `profile_ids`: one or more ids from the positioning view;
- `requirement_terms`: one or more exact terms from S1 `must_have` or
  `nice_to_have`;
- `jd_quotes`: one or more exact quotes already present in the validated S1
  evidence pool.

The deterministic parser rejects malformed JSON, markdown fences, missing or
unexpected fields, wrong types, empty strings/lists, duplicate normalized
sentences, duplicate ids/terms/quotes within a point, fewer than two points, or
more than four points.

Semantic validation proves that every profile id exists, every requirement term
is an exact S1 term, and every quote is an exact member of the S1 quote pool. The
model may write the advisory sentence, but it cannot cite an invented candidate
asset or unobserved JD evidence.

The human-readable positioning brief is the four-or-fewer `sentence` values
joined in order. G3 will later display them verbatim.

## 6. S2 contract

### 6.1 Request

`S2Request` contains:

- `job_id`, `company`, and `title`;
- validated S1 and S0 artifacts;
- the validated `SelectionCatalog`.

S2 never sees bullet prose. Its task is selection, not rewriting.

### 6.2 Response

`S2Response` contains:

- `base_variant`: one catalog variant;
- `projects`: ordered `ProjectChoice` objects, each carrying `project_id`, a
  short `reason`, and one or more zero-based `s0_point_indexes`;
- `bullet_order`: ordered, globally unique bullet ids;
- `coverage`: exactly one `CoverageEntry` for every S1 `must_have` term.

Each `CoverageEntry` contains:

- `term`: exact S1 term;
- `status`: `covered` or `gap`;
- `bullet_ids`: nonempty for `covered`, empty for `gap`.

The gap list is derived from the coverage table. It is not a second model-owned
field that can drift.

## 7. Deterministic S2 validation

Publication of `s2.json` requires all of the following:

1. The chosen base variant exists. The scorer-recommended variant is advisory,
   not a hard lock, but both values remain visible in the artifact.
2. Project ids are unique, known, and refer only to projects.
3. The selected project count equals the chosen base variant's project count.
4. At most one project is swapped relative to the chosen base variant: no more
   than one removed and no more than one added.
5. Every `ProjectChoice` cites valid S0 point indexes; every selected project has
   exactly one choice record.
6. `bullet_order` contains exactly as many bullets as the chosen base variant,
   with no duplicates.
7. Every bullet id exists in the catalog and is unblocked.
8. Project-owned bullets belong to selected projects. Experience-owned bullets
   belong to experience entries already represented by the base variant. Every
   selected project owns at least one selected bullet; an empty project heading
   is invalid.
9. Experience entry order and per-entry bullet counts remain identical to the
   chosen base variant. Experience is not removable or reorderable in S2.
10. Within each owner, selected bullet priorities are nondecreasing. A lower
    priority bullet cannot precede a stronger one from the same owner.
11. Coverage contains every S1 `must_have` term exactly once and no other term.
12. A `gap` has no bullet ids. A `covered` entry has at least one bullet id, and
    every cited bullet appears in `bullet_order`.
13. Each covered term matches at least one cited bullet's `keywords_hit` after
    case-folding and whitespace collapsing. Free semantic inference is not
    accepted as coverage.
14. Any S1 term colliding with `do_not_claim` under the same normalisation must
    be a `gap`.

These checks are pure and return bounded, stable diagnostics. Schema validity
alone is never sufficient.

## 8. Invocation, tracing, and outcome classification

`src/tailor/invoke.py` gains a stage-neutral `invoke_text_model()` while
retaining `invoke_s1_model()` and `DEFAULT_S1_CLAUDE_CMD` as compatibility
wrappers/aliases. S1 behavior and tests must remain unchanged.

S0 and S2 each get a narrow pipeline with the same five outcomes used by S1
where applicable:

- `invocation_failure`
- `parse_failure`
- `semantic_failure`
- `validation_failure` (S2 only, for deterministic selection constraints)
- `valid`

S0/S2 inputs contain no raw third-party JD instructions; a nonempty S1
`suspected_injection` could not have produced an authoritative `s1.json` in
M8P-1. No additional injection override is introduced.

## 9. File contracts and CLI

The one-job operator sequence is:

```text
existing: s1_request.json + s1.json
  -> prepare
     -> s0_request.json + s2_catalog.json
  -> invoke-s0
     -> s0.json
  -> prepare-s2
     -> s2_request.json
  -> invoke-s2
     -> s2.json
```

The CLI is `python -m scripts.tailor_s0_s2` with four commands:

1. `prepare --job-id ID --db PATH --s1-request PATH --s1 PATH --profile PATH --output DIR`
2. `invoke-s0 --request PATH --output DIR [--dry-run]`
3. `prepare-s2 --s1-request PATH --s1 PATH --s0 PATH --s0-request PATH --catalog PATH --output DIR`
4. `invoke-s2 --request PATH --output DIR [--dry-run]`

`prepare` opens SQLite read-only, re-runs the M8P-1 eligibility boundary,
proves the persisted S1 request still matches the eligible DB row, strictly
re-validates `s1.json` against that JD, and obtains the DB's recommended base
variant. It then atomically writes deterministic preparation artifacts.

`prepare-s2` proves that S0, S1, and the catalog belong to the same job,
strictly revalidates `s1.json` against the original JD in `s1_request.json`,
and then atomically writes `s2_request.json`. The S2 model prompt still omits
the raw JD; the original request is used only by deterministic validation.

Both invoke commands support a true dry run: validate and build the prompt, but
make no model call and write no trace or accepted artifact. Real invocations
publish only on `valid`; an existing accepted artifact survives a failed rerun.

## 10. Explicit non-goals

M8P-2 does not implement or start:

- S3 bullet/skills alignment or any free-text resume change;
- the missing G1 L1/L4 checks or modification of existing lints;
- G2 critic/revision loops;
- G3 review packets, taste capture, or gap aggregation;
- PDF rendering or archival/application directory generation;
- database mutation or a `TAILORED` transition;
- Company Bank Track C or any company-bank lookup;
- live model calls, the three-job pilot, or the 30-resume run;
- M9F-1, M9D-1, discovery, ingestion, scoring, or eligibility changes;
- dependency additions or prompt retries.

## 11. Acceptance criteria

- All new parsers and validators are pure and covered by fixture/unit tests.
- All model subprocess calls are mocked in tests.
- S0 rejects invented profile ids, terms, and quotes.
- S2 rejects every invalid reference/selection/coverage condition in section 7.
- Dry runs create no model calls, traces, or accepted artifacts.
- Failed reruns preserve prior accepted artifacts.
- The three pilot jobs pass the read-only M8P-1 eligibility preparation gate,
  and both real-profile projections build and round-trip offline. Full M8P-2
  request preparation remains correctly gated on a live, accepted `s1.json`.
- `pytest -q` passes, `git diff --check` is clean, and `data/jobs.db` remains
  byte-identical.
- Documentation names M8P-2 complete only after implementation and verification;
  no live-pilot claim is made.
